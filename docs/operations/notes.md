# Explicit notes and corrections

`/memory remember <text>` stores an explicit note for the canonical current workspace. `/memory correct <text>` stores a correction in the same scope. `pi_memory_note` accepts `action: remember|correct`, text and scope; `workspace` resolves to the current workspace, while `global` or an explicit scope label is retained as evidence metadata. The tool description requires an explicit user request. It has no delete action. Scope labels do not grant filesystem access.

Notes are shared between versions and persist independently of generated summaries. The host records command/tool origin, consumer session and foreground run, plus the matching user-message entry when available. Caller-supplied provenance is never used. Commands outside a foreground run may have no run/message pointer. Known credential shapes and signed/access-bearing URL values in text or scope are redacted before hashing and persistence. Text is limited to 16 KiB; files are private, fsynced before the short SQLite commit and recovered after interruption. Explicit notes respect disabled/excluded stores and explicit off/read mode flags; disabling automatic generation preserves the note and pauses model work. Model tool results expose note ID/action/scope and correction blocking state, without internal note paths or database details.

A correction commits its note, advances the shared control epoch, blocks both pipelines (including an inactive version), revokes generated views and fences obsolete consolidators in one transaction. Local reader pins are cleared immediately; other processes reject them at the next retrieval boundary. Revoked files are cleaned after the commit and on startup. Cleanup failure leaves reading blocked. A failed provider cannot restore old guidance.

Each enabled version independently consolidates active notes and eligible same-version evidence, validates its outputs and publishes at the new epoch. Pending explicit notes and note-forget revocations schedule consolidation even in RPC/JSON/print modes outside `captureModes`; automatic transcript capture and extraction remain restricted by that setting. Generation, exclusion, idle and budget policies still apply. `note_applications` records the applied hash/generation separately for v1 and v2. Completing v1 never reconciles v2. A later explicit activation can rebuild the still-blocked inactive version.

The staged manifest includes note action, scope and creation order. Adapted Pi writer instructions give corrections priority over conflicting older evidence and generated text; later corrections control conflicts in their scope, while unrelated notes remain active. Note timestamps preserve committed creation order even if the wall clock repeats or moves backward. This is a writer behavior contract, not proof of arbitrary model semantic correctness.

`/memory forget note <note-id>` removes exactly that note's evidence and revokes both generated views before rebuilding. Its result explains that older independently supported source evidence may become applicable again. It does not suppress every source about the same subject; use a replacement correction or a concrete source-forget command for that intent. Source/session/clear controls belong to the subsequent forgetting work.

Schema 10 adds nullable session/run/message provenance and an origin field. Existing schema 9 notes keep their text, hash, scope and per-version applications; legacy provenance remains unknown. Vendored upstream prompts are unchanged.
