# v1 consolidation and publication

Issue #7 connects existing v1 extractions to a private consolidation Agent and the next session's `pi_memory` prompt section. Development and verification use a fake Pi/model boundary with real temporary Git repositories, JSONL and SQLite; those checks do not establish real-model memory quality.

Automatic work uses one-shot scheduling and pauses new requests while foreground work is active. `/memory run --now` runs eligible extraction followed by consolidation passes for the selected write targets; both phases share the configured daily budgets. The selected version controls reading. Issue #8 adds v2 consolidation and publication through the shared scheduler, with one store-wide writer lease and separate generations. Issue #9 adds the three read-only detail tools described in [retrieval.md](retrieval.md). An unbuilt selected version never falls back to the other version.

Selection takes the newest valid same-version extraction per active lineage, up to 256 sources. The v1 scheduler honors lower `schedule.maxConsolidationSources` values and caps larger valid configurations at this policy ceiling. Eligibility uses the version-specific last real use, or source time for never-used evidence, within 30 days by default. Sources are ranked by usage, eligibility time and source ID; raw memories are merged in source-ID order. Injecting the summary does not increment source usage.

The writer sees only staged evidence, shared notes, supported prior outputs and a deterministic workspace diff. Its only tools are `workspace_list`, `workspace_read`, `workspace_search`, `workspace_write` and `workspace_delete`. Evidence and notes are read-only; output writes are restricted to `MEMORY.md`, `memory_summary.md` and `skills/<slug>/SKILL.md`. Absolute/traversing paths, symlinks, devices and other writes are rejected. There is no shell, original transcript access, project-resource discovery, extension loading or recursive delegation in the writer.

Content hashes cover version, selection and retention policy, prompts, notes, shared epoch and generated outputs. Unchanged content skips the model. A complete changed-path index replaces a unified diff above 4 MiB. When prior support expires or is revoked, the diff contains paths only and never copies prior learning or evidence plaintext. The manifest records the fallback reason.

The Writer uses Pi's `createAgentSession()` with in-memory history, an isolated resource loader and only the workspace tools. Pi owns threshold compaction, overflow recovery and transient retries. Each request, including compaction and retries, reserves the shared daily budget. Missing provider usage keeps the conservative reservation. There are no custom 12-request, 40-tool, five-minute or 4,000-output-token caps, and no validator-feedback repair. Cancellation or failed validation discards unpublished staging.

Validation follows the pinned Codex contract: require the handbook file and a UTF-8 summary starting with literal `v1`. Heading order, project/date grouping, handbook fields, prose references and a 9,999-byte summary cap are not v1 rejection rules. Selected evidence/note integrity, physical allowlists and secret scanning remain separate host safeguards. No remaining evidence or notes produces deterministic minimal files. Semantic evaluation, not format validation, checks claims. See [strict-port ledger](../strict-codex-port.md) for host adaptations and verification boundaries.

Publication fsyncs every file and directory, renames to a unique immutable generation on the same filesystem, then advances the sole SQLite pointer in one CAS transaction. CAS rechecks the lease fence, actual publication time, per-version base, selected inputs and shared epoch. A failed CAS leaves an unserved orphan. Recovery cleanup respects a live consolidator and supplied reader pins; ordinary retention keeps the current generation and two old generations. Privacy revocation overrides that retention.

At `before_agent_start`, local reads verify the selected generation, epoch, current retention policy, manifest hash and summary hash/contract. Invalid, excluded or unavailable memory is omitted. The section includes version, generation ID, current workspace, applicability and historical-evidence labeling; no memory model request occurs on the prompt path. A retention deadline arms a one-shot invalidation/rebuild wakeup. The runtime diagnoses hosts without structured prompt sections and does not replace an opaque full prompt.

Schema 9 adds version-aware generations, selection/use statistics, shared-note metadata and consolidation state. The migration preserves schema 8 extraction rows and does not modify vendored upstream prompts.

Schema 14 preserves existing rows and provenance triggers while allowing the native v2 9,000-byte head/tail truncation marker to grow the accepted output beyond 9,000 bytes. Back up a schema-13 store before upgrading; an older runtime must use that backup for rollback.
